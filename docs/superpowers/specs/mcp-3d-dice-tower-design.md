# Развитие KOMPAS MCP: 3D → сборка → чертежи

Дата: 11 октября 2026 года.
Репозиторий: `C:\Users\user\DevProjects\MCP-Kompas-3D`.

## Цель и согласованный контекст

Развить существующий MCP до переиспользуемого инструмента работы с КОМПАС-3D. Dice tower в стиле «Рика и Морти» — учебный сквозной сценарий, на котором проверяются возможности сервера. Пользователь подтвердил предложенную конструкцию и уточнил, что основная цель — разработка полноценного MCP.

В этой итерации «полноценный» означает проверенную цепочку создания параметрических деталей, сборки и связанных чертежей. Это не обещание покрытия всего SDK КОМПАС: поверхности, листовой металл, CAM и прочие подсистемы не входят в эту итерацию.

## Подтверждённое исходное состояние

- Зарегистрированный MCP публикует 41 команду для 2D. Публичных команд 3D нет.
- `Adapter._doc` допускает только документ типа 2D; существующие методы нельзя просто использовать для модели.
- FastMCP вызывает адаптер через единственный COM STA worker. При тайм-ауте исход операции остаётся неизвестным, автоматический повтор недопустим.
- SDK v21 доступен по настроенному пути `D:/ASCON/KOMPAS-3D v21/SDK`; наличие интерфейсов на диске не доказывает работоспособность операций.
- Прямая работа с SDK разрешена как этап разработки/диагностики. Итоговые команды должны иметь типизированные схемы MCP и пройти проверку через протокол.

## Выбранный подход

Добавить специализированные, но универсальные команды 3D поверх существующего адаптера и STA worker. Рецепт башни хранить в примере клиента и описании параметров, а не зашивать её геометрию в сервер.

Альтернативы: генератор только одной башни даст меньше переиспользуемых возможностей; публичное выполнение произвольного Python разрушит типизированный контракт. Выбранный подход позволяет последовательно наращивать API и проверять каждую поддержанную операцию.

## Границы модулей и команд

Предварительные имена команд уточняются при изучении SDK; их назначение фиксировано:

1. **Документы и диагностика.** Создание детали и сборки; открытие, состояние, сохранение и явное закрытие собственных документов. Состояние включает тип, путь, признак изменений и перечень доступных возможностей. Существующие команды 2D сохраняют совместимость.
2. **Эскизы.** Создание эскиза на стандартной плоскости либо плоской грани; замкнутые профили из отрезков и окружностей; чтение созданной геометрии. Начальный обязательный набор плоскостей — XY, XZ, YZ. Единицы — мм и градусы; система координат указана в схеме и результатах.
3. **Формообразование.** Выдавливание, вырез выдавливанием, чтение дерева операций и тел, габаритов и объёма. Ссылки на эскизы/операции принадлежат конкретному документу и сессии. Выбор граней по нестабильному индексу не используется как долговременная идентичность.
4. **Параметры и обновление.** Чтение и изменение поддержанных размеров операций, перестроение и проверка фактического результата. Ошибки перестроения возвращаются явно; документ не считается корректным только по возвращённому `True`.
5. **Сборка.** Вставка сохранённых деталей, установка и чтение положения компонентов, перечень компонентов. Минимум — воспроизводимое размещение без сопряжений; такой способ явно описан. Сопряжения добавляются только после собственной SDK-проверки и не являются условием завершения этой итерации.
6. **Чертежи по модели.** Создание связанных ортогональных видов и разреза, обновление при изменении модели, нативные размеры и оформление существующими 2D-командами. Вид должен сохранять ссылку на модель; ручные проекции не принимаются за ассоциативный результат.
7. **Экспорт.** Нативные модели КОМПАС, STL деталей для печати; CDW и PDF чертежей. STEP добавляется при подтверждении доступного конвертера; его отсутствие явно фиксируется и не блокирует обязательные форматы.

Новые модули отделяют 3D-документы, геометрию, сборки и виды чертежей от существующих 2D-операций. Реестр хранит типизированные ссылки без передачи COM-объектов между потоками. Публичного `execute_python` не будет.

## Учебная башня

Концепция — «Портальная лаборатория Рика»: прямоугольная башня, три чередующихся наклонных перегородки, выход через декоративный портал и съёмный лоток. Тематика выражается рельефными лабораторными панелями, портальной рамкой и упрощёнными силуэтами Рика и Морти. Декор состоит из реальной геометрии модели.

Начальные учебные параметры: высота корпуса 220 мм, внешнее сечение 90 × 90 мм, стенка 3 мм, кубики с номинальным размером до 22 мм. Три перегородки расположены на разных высотах с наклоном примерно 35° и направляют кубик попеременно к противоположным стенкам. Проходы рассчитываются с учётом диагонали кубика и технологического запаса; одной проверки ширины по ребру недостаточно. Габариты лотка и портальной рамки задаются отдельно.

Детали: корпус, съёмная сервисная стенка, перегородки, лоток, декоративная портальная рамка. Соединения проектируются для разборки; посадочный зазор задаётся параметром. Точные высоты перегородок, отверстия и посадки определяются расчётом проходов в реализации и записываются в параметрах примера. Это учебный проект, физическая работоспособность подтверждается только после изготовления.

## Критерии приёмки

1. Старые 2D-команды и их тесты продолжают работать.
2. Отдельная универсальная тестовая деталь создаётся новыми командами; её объём и габариты сверяются с расчётом. Проверяется изменение размера и перестроение.
3. Неверные значения, чужие/устаревшие ссылки и неподходящие типы документа отклоняются до опасной мутации. Частичное создание и неизвестный исход операции диагностируются.
4. 3D-деталь, сборка и чертёж сохраняются и читаются после безопасного закрытия/открытия. Подтверждаются геометрия, состав компонентов и связи видов.
5. Изменение одного размера исходной модели меняет связанный вид после обновления. В разрезе видны внутренние перегородки.
6. Реальный MCP-протокол проверяет `initialize`, `tools/list`, `tools/call`, корректные и отрицательные сценарии. Прямой SDK-probe не заменяет этот этап.
7. Экспорты проверяются по свежему файлу и содержимому. Чертежи проверяются визуально по PNG: читаемость размеров, разрез, размещение видов и отсутствие наложений.
8. Башня строится рецептом, использующим универсальные команды. Документация содержит только проверенные возможности.

## Порядок дальнейшей работы

После согласования этой спецификации составить план реализации. Затем изучить точные интерфейсы установленного SDK и проверить операции напрямую на отдельных документах; включить их в MCP; проверить через протокол; построить башню и связанные чертежи; обновить документацию и навык. Прямой COM и зарегистрированный MCP не запускаются одновременно. Изменения пользовательских документов и публикация репозитория не входят в задачу.
