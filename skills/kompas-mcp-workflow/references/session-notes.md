## 1. Что запускать и в каком порядке

**Предпочтительный порядок: самостоятельно запустить КОМПАС, затем подключить MCP, проверить документ и только потом чертить.** В этой сессии запуск приложения агентом через установленный ярлык и новое MCP-подключение позволили продолжить работу после зависаний. Это проверенный порядок действий, но не доказательство того, что один лишь запуск приложения устраняет все ошибки.

Под «самостоятельно» имеется в виду, что агент запускает приложение явно, без просьбы к пользователю открыть его вручную и без надежды на неявный запуск через COM.

Установленный КОМПАС:

```text
D:\ASCON\KOMPAS-3D v21\Bin\KOMPAS.exe
```

Ярлык:

```text
C:\Users\Public\Desktop\КОМПАС-3D v21.lnk
```

Выполни запуск через инструмент выполнения команд с PowerShell. Если среда ограничивает доступ к рабочему столу, используй штатный механизм эскалации команды в рамках разрешённой пользователем задачи. Команда:

```powershell
Start-Process -FilePath 'D:\ASCON\KOMPAS-3D v21\Bin\KOMPAS.exe' -WindowStyle Normal
```

Можно запустить и установленный ярлык. Если путь неизвестен, прочитать его, а не угадывать версию по названию папки:

```powershell
$shortcut = (New-Object -ComObject WScript.Shell).CreateShortcut(
    'C:\Users\Public\Desktop\КОМПАС-3D v21.lnk'
)
$shortcut.TargetPath
```

На этом компьютере в `C:\Program Files\ASCON` есть другие продукты и версия v23 Home. Нужная v21 находится на диске D. Поиск только в Program Files дал бы неправильный результат.

Приложение, которое пользователь попросил открыть, запускается видимо. Служебный MCP-процесс запускается без отдельного окна.

## 3. Доступность сервера и возможность чертить — разные проверки

Минимальная последовательность:

1. `bridge_status({})` — отвечает ли сервер и разрешены ли инструменты.
2. `list_open_documents({compact: true})` — видит ли он документы.
3. `get_active_document({compact: true})` — тот ли документ активен.
4. `preflight_context` с `target="2d"`, `scope="deep"`, `include_view_metadata=true`, `response_profile="debug"` — доступность API5/API7 и фактические параметры вида.

В начале сессии `bridge_status` вернул `authorized_ready`, 113 разрешённых инструментов и отсутствие ошибки политики. Но создание документа затем завершилось внутренней ошибкой API5. Поэтому статус авторизации сам по себе **не подтверждает**, что КОМПАС доступен для построения.

`list_open_documents` с `count=0` означает отсутствие документов, видимых этому подключению. Нельзя делать вывод, что пользователь вообще не открыл чертёж: в сессии наблюдались два процесса КОМПАСа, и контекст подключения необходимо проверять явно.

## 4. Зачем нужен локальный Python-скрипт

Обычно сначала использовать подключённые MCP-инструменты. В этой сессии встроенные запросы зависали: не отвечали даже чтение активного документа и статус сервера. При этом новый локальный клиент, запускающий тот же EXE по стандартному MCP stdio, отвечал и работал.

Скрипт нужен для:

- нового стандартного подключения, если прежнее зависло;
- последовательного выполнения большого набора операций;
- записи точных координат, размеров и подписей в JSON;
- продолжения с последней подтверждённой операции;
- диагностики ответов и тайм-аутов.

**Это клиент MCP, а не прямой доступ к COM и не обход разрешений сервера.** Каждый запрос остаётся `tools/call` и проходит проверку политики. Если сервер запрещает инструмент, скрипт не делает его разрешённым.

Рядом с памяткой сохранён `mcp_client.py` — клиент, использованный в сессии. Без аргументов он читает активный документ и снимок состояния. С аргументом он выполняет массив операций из JSON-файла. Это диагностический пример: перед повторным построением внимательно проверить список операций.

Из директории этой памятки выполни диагностическую проверку через инструмент выполнения команд:

```powershell
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' `
  '.\mcp_client.py'
```

Подготовив и проверив JSON самостоятельно, выполни набор действий:

```powershell
& 'C:\Users\user\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' `
  '.\mcp_client.py' '.\actions.json'
```

Рабочий запуск из среды агента выполнялся вне ограниченной песочницы через механизм одобрения команд. Если запуск блокируется, использовать предусмотренный механизм разрешений, а не пытаться обходить ограничения.

## 5. Как устроен клиент

Сервер запускается дочерним процессом:

```python
p = subprocess.Popen(
    [str(base / 'kompas-mcp.exe')],
    cwd=base,
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
    encoding='utf-8',
    errors='replace',
    creationflags=subprocess.CREATE_NO_WINDOW,
)
```

Затем отправляется JSON-RPC `initialize` с `protocolVersion="2024-11-05"`, пустыми capabilities и clientInfo. После успешного ответа отправляется уведомление `notifications/initialized`. Эта версия протокола была принята установленным сервером; при обновлениях учитывать согласованную сервером версию.

Далее запрос имеет такой вид:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "list_open_documents",
    "arguments": {"compact": true}
  }
}
```

Каждое сообщение — JSON плюс перевод строки. После записи нужен `flush()`. Ответ сопоставляется с запросом по `id`, а не просто берётся первая строка stdout.

Stdout и stderr читать параллельно, чтобы заполненный pipe не заблокировал сервер. В приложенном клиенте stderr вычитывается и отбрасывается; при расследовании нового сбоя лучше сохранять его в отдельный диагностический журнал, не публикуя секреты.

В `finally` завершать только дочерний сервер, запущенный этим скриптом. Не убивать все процессы `kompas-mcp` или КОМПАСа: они могут относиться к другим подключениям и документам.

## 6. Формат JSON-файла действий

Файл — массив, операции выполняются последовательно:

```json
[
  {
    "name": "set_active_view",
    "arguments": {"view_number": 2, "compact": true}
  },
  {
    "name": "create_rectangle",
    "arguments": {
      "x": 0, "y": 0,
      "width": 25000, "height": 5850,
      "style": 1, "compact": true
    }
  },
  {
    "name": "create_text",
    "arguments": {
      "text": "Охлаждающий тоннель",
      "x": 10849, "y": 1290,
      "height": 3.5, "compact": true
    }
  }
]
```

Это пример отдельных операций, не полный готовый план. Не запускать его вслепую в произвольном документе.

Полезно отдельно писать генератор списка действий и клиент для их исполнения. Генератор вычисляет координаты без изменения чертежа; клиент выполняет подготовленный JSON. Перед исполнением проверить полученный файл.

В генераторе назвать первый аргумент помощника `tool_name`, а не `name`: у `create_view` есть собственный параметр `name`. В этой сессии функция `call(name, **kwargs)` вызвала `TypeError: got multiple values for argument 'name'`.

## 7. Ответы надо проверять глубже, чем isError

Есть несколько уровней результата:

- JSON-RPC `error` — ошибка запроса;
- MCP `result.isError` — ошибка инструмента;
- `structuredContent`, если присутствует;
- JSON внутри `content` блока типа `text` — результат операции.

**`isError=false` не означает успех операции.** В сессии `save_document` возвращал `success=false` при `isError=false`. `set_active_view` тоже иногда сообщал `success=false`, но последующая проверка показывала нужный активный вид. Поэтому читать результат операции и проверять состояние документа после неё.

В приложенном клиенте автоматическая остановка реализована только для JSON-RPC `error` и MCP `isError`. Он не останавливается на вложенном `success=false`: это известное ограничение примера, а не рекомендуемая проверка для полностью автоматического построения. Для такой автоматизации добавить разбор текстового JSON и проверку ожидаемых результатов после каждого важного этапа.

Если инструмент вернул отказ политики, не повторять его через другой канал в попытке обойти запрет. В этой сессии `execute_python_script` существовал в каталоге схем, но выполнение вернуло `tool_not_allowed`. Наличие схемы в `describe_tool` не равно разрешению на вызов.

## 8. Главный нюанс: создать вид недостаточно, нужно проверить его масштаб

Вызов `create_view(scale=0.02)` вернул успех, но фактически создал вид с масштабом **1.0**, то есть 1:1. Это подтвердил подробный `preflight_context` через API7. Проблема воспроизвелась и для нового второго вида.

Рабочая последовательность:

1. Создать новый вид с нужным именем, номером и точкой привязки.
2. Получить его актуальный `api5_reference` из подробного `preflight_context`.
3. Выполнить `transform_object` **над объектом вида**, задав `scale_x=0.02`, `scale_y=0.02`, `origin_x=0`, `origin_y=0`.
4. Повторно проверить, что `active_view.scale` действительно равен `0.02`.
5. Создать геометрию в реальных миллиметрах в этом виде и проверить размеры.

Пример, где число reference нужно заменить свежим значением:

```json
{
  "name": "transform_object",
  "arguments": {
    "reference": 1073741876,
    "scale_x": 0.02,
    "scale_y": 0.02,
    "origin_x": 0,
    "origin_y": 0,
    "compact": true
  }
}
```

В сессии после этого API7 подтвердил масштаб 1:50, а прямоугольник помещения остался 25000×5850 мм в координатах владельца. Значение reference выше — историческое, не пригодное для повторного использования без проверки.

**Не уменьшать каждый прямоугольник в 50 раз вместо изменения вида:** тогда размеры модели станут неверными. Масштаб относится к отображению вида на листе; геометрия хранит реальные размеры.

Параметры `origin_x/y` этого инструмента нельзя считать без проверки обычным центром масштабирования. При значениях 160/250 в первом эксперименте точка привязки вида изменилась с 160/250 на 320/500. Нулевые значения сохранили требуемую привязку 160/250 во втором виде. Это наблюдение реализации данного инструмента.

В официальном SDK свойство масштаба интерфейса `ksViewParam` называется `scale_`. Это может быть связано с ошибкой обёртки, но её исходный код не исследовался и причина не доказана: [справка АСКОН](https://help.ascon.ru/KOMPAS_SDK/25/ru-RU/ksviewparam_scale_.html).

## 9. Координаты и подписи

Для плана используется отдельный вид с началом на листе `(160, 250)` и масштабом `0.02`. Внутри вида координаты оборудования — реальные миллиметры. Тогда помещение 25000×5850 мм занимает на листе 500×117 мм.

Для чтения выбирать систему координат явно: `owner`, `view` или `sheet`. Если ответ неожиданно совпадает с координатами владельца, не считать его самостоятельным подтверждением масштаба. В этой сессии решающей проверкой было `active_view.scale`, а не один лишь результат `list_objects` с `coordinate_space="sheet"`.

Подписи создавать после активации нужного вида. Для оборудования использовалась высота текста 2.5 мм, для длинных названий тоннеля и флоупака — 3.5 мм. После исправления масштаба растровая проверка показала читаемые подписи внутри оборудования. Не умножать высоту текста автоматически на 50: аннотационные объекты имеют отдельные правила масштабирования.

Для центрирования оценивалась ширина текста и сдвигалась точка начала. Это приблизительный метод, после него нужен просмотр результата.

Заголовок и общие примечания размещены в системном виде 0, координаты там — миллиметры листа. Геометрия, подписи оборудования и размерные линии находятся в новом виде 2.

Размеры помещения и отступа в данном чертеже выполнены линиями, засечками и текстом. **Это не ассоциативные размерные объекты:** при изменении геометрии их нужно обновить отдельно. Если нужны полноценные размеры КОМПАСа, использовать `create_linear_dimension` и проверить его ориентацию и положение.

## 10. Кириллица, символы и вывод

В Python обязательно:

```python
sys.stdout.reconfigure(encoding='utf-8', errors='replace')
```

Без этого вывод клиента шёл через cp1251 и завершился `UnicodeEncodeError` на символе `Ø`. Операция создания текста к этому моменту **уже успела выполниться**.

JSON-файлы записывать и читать как UTF-8. При отправке JSON-RPC стандартный `json.dumps` с экранированием не-ASCII символов подходит для кириллицы и специальных знаков. `ensure_ascii=False` удобен для читаемых файлов и журналов при согласованной UTF-8 кодировке.

Перед повторным запуском после ошибки вывода определить, какие операции уже произошли. Иначе появятся дубликаты. В сессии продолжение началось после последней фактически выполненной операции, включая текст, на печати ответа которого упал клиент.

Из ответов `screenshot_document` убирать base64 изображения перед печатью журнала. Сам файл изображения сохраняет инструмент. Иначе одна строка вывода может занять десятки тысяч токенов.

## 12. Лист и визуальная проверка

Новый документ с настройками по умолчанию оказался **А4 вертикальным**. Запрос пользователя «А1 горизонтальный» не установил этот формат автоматически: у доступного набора инструментов не обнаружилось разрешённого средства настройки листа, а диагностический Python-инструмент был запрещён политикой сервера.

Не обещать автоматическую смену формата без соответствующего инструмента и проверки. В конце пользователь явно взял оформление листа на себя; масштаб вида и подписи были закончены независимо от этого.

Пока лист А4, часть плана находится вне его рамки. После выбора А1 горизонтального план шириной 500 мм можно разместить на листе 841×594 мм; окончательное оформление и расположение проверяются визуально.

`screenshot_document` в этой сессии работал двумя способами:

- `capture_mode="viewport"` — изображение окна с интерфейсом; может показывать лишь часть документа;
- `capture_mode="2d_graphic_raster"` — растровое изображение чертежа; итоговая проверка показала весь план, подписи и текущую рамку А4.

Изображение окна не считать полным экспортом листа. Читать `capture_mode`, а затем открывать сохранённый PNG для проверки.

## 13. Если запрос завис

1. Проверить, не открыто ли модальное окно в КОМПАСе. В этой сессии пользователь подтвердил отсутствие диалогов.
2. Не отправлять пачку новых изменяющих команд в зависшее соединение.
3. Отмена ожидающего вызова со стороны клиента не доказывает отмену операции внутри сервера.
